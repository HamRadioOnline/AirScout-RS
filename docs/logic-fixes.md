# Logic fixes: stage 6 approval lists

Stage 6 fixes the defects that the port reproduced on purpose (`docs/logic-findings.md`). Design:
`docs/superpowers/specs/2026-11-25-stage6-logic-fixes-design.md`. This file holds one section per area. The owner
approves each area's list before any fix of that area ships. Nothing in an area is fixed before that.

Upstream cites use `dl2alf/AirScout` at `fbadef0f`. Rust cites use `path:line`.

The fixes are not reported upstream during stage 6. They will be offered to DL2ALF later, one by one, as C#
pull requests from a fork of `dl2alf/AirScout`. Each fixed row's implementation record (C# location, the fix in
C# terms, the proving test) is the source for that pull request.

## Columns

| Column | Meaning |
|--------|---------|
| `#` | The row number in `docs/logic-findings.md`. New findings get the next free number (#343 first). |
| Problem | What is wrong, in one sentence, with the Rust location of the port. |
| Fix proposal | What the fix does. Every `fix` names where the new expected value comes from: a hand-worked case, or a cited independent reference (Karney/`geographiclib`, an ITU-R recommendation with number and section). For large composites it is invariants plus spot values. It is never the fixed Rust code. |
| Effect for the user | What the user sees change. |
| Golden delta | The affected cases as `<file>.json:<case name>`, with the size of the change (measured or bounded). `none` if no golden case is touched. |
| Decision | `fix`, `keep` (with the reason) or `owner`. In the review part it holds the proposal, written `proposed: fix`, `proposed: keep — <reason>` or `owner — <question>`. Only the owner's approval turns it into the final value. |

Golden cases have no names. `<file>.json:<fn>[i]` names the case at index `i` of the file's whole `cases` array (0-based, counted over all functions in the file, not per function); `<fn>` only says which function that case calls. For example, `latlon.json:distance[690]` is entry 690 of the `cases` array of `latlon.json`, and that entry is a `distance` case.

### Persisted data: algorithm-version bump

The spec ("Persisted data") requires a version on caches of computed results. Stage 6 sets explicit algorithm versions in all three caches. The final antimeridian coverage fix bumps each version to 2 so rows computed against falsely complete coverage are discarded. The ASTER filter fix bumps each version again to 3 because it changes results at the existing halved-step keys. Three caches hold computed results, all keyed by their inputs. `ElevationPath` (elevation database per model, `crates/as-elevation/src/path.rs:123-126`) holds the profile samples. `PropagationPath` (`crates/as-propagation/src/engine.rs:22-28`) holds `eps1_min` and `eps2_min`. `PropagationHorizon` (`crates/as-propagation/src/horizon.rs:13-17`) holds the 360 horizon points. A fix that changes a stored value without changing its key needs the bump; a bump of `ElevationPath` also bumps the two tables computed from it.

- `ElevationPath`: #10 (edge samples), #289 (entries with 0 m for a skipped square), #7 option B (positions of every sample).
- `PropagationPath`: #349, #350, and everything that bumps `ElevationPath`. #354 changes the key itself.
- `PropagationHorizon`: #3, and everything that bumps `ElevationPath`. #354 changes the key itself.
- No bump: #1 and #352 (info points are computed on load), #2, #343, #344 (crossings are computed live; the review found no persisted crossing cache), #4, #5 (the in-memory tile cache holds raw tiles), #8 and #11 (the obstruction and the horizon flag are applied on load, `crates/as-propagation/src/engine.rs:231`, `crates/as-propagation/src/horizon.rs:292`), #15 and #346 (the old results failed or were invalid and were not stored), #282 (`horizon-gen` does not save paths, `crates/as-cli/src/horizon_gen.rs:111`), #345, #347, #348, #353. #351 option B originally changed only the step width key. The final ASTER fix changes the filtered results for that same key.

The migrations recreate the three computed tables in SQLite transactions and keep the source tile and obstruction tables. Each lookup checks its table's algorithm version. A later computation replaces an older-version row for the same key regardless of its timestamp. Propagation keys add `NearField` in metres. Path and horizon operations use one near-field snapshot for the lookup, computation and write.
